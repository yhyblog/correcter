# GPU占卡覆盖：八卡持续利用率（2026-09-21）

用户最新明确要求同时使用8张卡，并说明整机GPU利用率低于50%后可能被停机；本条覆盖旧“formal wave期间所有holder必须停算、禁止idle-subset holder”的占卡规则。A已经按本要求启动Batch3临时监督，本次记录该用户覆盖，不将其伪称为旧release原有行为。阈值50%为用户提供，平台具体聚合方式/时间窗口尚未知；95% duty是holder配置，不等于已测得95%利用率或防关机保证。

1. 优先安排已授权真实任务填满8卡；资源不足、尚未开始或已经结束且无正式GPU活动的卡，允许在formal wave/队列运行期间由受控辅助holder补位。A/B独立生效，B状态不得阻塞A；不扩大原科学矩阵、样本、seed、并发或训练授权。
2. 正式计算优先。未来queue-aware入口对指定GPU执行“停止并确认自有holder及后代退出 → 正式GPU进入”的明确交接，并在加载/正式活动期间保持该卡holder停止；不得仅凭低利用率就给正在加载、暂时CPU阻塞或等待下一分支的正式GPU添holder，不终止无关进程。
3. 当前Batch3不热改冻结launcher、guard或formal.lock，不重复命令、增并发或改变采集器。其现有临时监督独立记账，读取原保存事件并及时让出GPU。监听START后发停止指令不等于证明正式GPU进入前已经退出；需要保存各自事件时间与已存在的加载/绑定时间作审计，缺证据就标unknown，不补造原子交接。若不能确认未来待用卡可及时让出，只在已完成且后代退出的卡补位，并按其余可用卡维持利用率；不要为审计追加模型或仿真。
4. 临时holder只归本node监督管理，按host/boot/PID/start_ticks和GPU UUID核对；正式波次退出后先停止临时holder并确认退出，再交回原guard，避免双重占用。后台队列可用同一个经过检查的本地监督管理空闲卡，保留现有预约/单锁机制，不嵌套formal.lock。机器重启按身份恢复，不重跑正式作业。
5. 辅助holder的开始/停止/退出、卡号与UUID、duty、利用率观测、异常和交接成本单独记账。科学116caps保持，不能再把整个wave说成全8holder持续停算，也不能因科学模型调用0把包含holder的真实GPU活动报0。利用率优先复用已有缓存/日志，必要控制面查询按既定监测预算独立记录。
6. Batch3回执记录覆盖时间、受影响卡和区间、让出与最终恢复证据。混合占卡时段的wall time/资源竞争条件须披露；不直接和无holder运行比较算法延迟、time-per-success或吞吐。不因此自动废弃样本或重跑，状态/标签/账本资格照原规则独立核验。

这是调度/辅助占卡覆盖，不是新科学计算release，也不要求重新生成队列源计划或重新审批每一批。原AUTHORIZATION_V2及源/预算SHA保留；本补充由queue CONTROL.operational_overrides绑定并优先于其中相冲突的holder条款。实施端在现有bootstrap/join任务中读取本补充，做必要控制面交接检查和实际记录即可，不另建长审批链。
