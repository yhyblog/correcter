# 存储候选的定向依赖核查

此为 A/B 预检修正任务的 CPU 附项，只核查两份 `STORAGE_CANDIDATES.json` 中已有候选；不扩展全盘扫描、不删除。分析端决定记录见 `manifests/STORAGE_DECISIONS_V1.json`。

当前决定：4个已确认输入 keep；9个 Smol 中间 checkpoint 与2个 X-VLA 下载残片候选 defer，等待以下具体证据。

- A：确认9个 Smol 005000…045000 checkpoint 是否属于正在使用/需复现的选定模型或恢复链；050000 保留且新 E8 不进行 checkpoint sweep。指出具体活跃/封存依赖，或确认不存在。若可清理，列出可删大 payload 的精确文件身份，保留小配置、训练沿革及日志；不要只因历史库存清单提到路径就判定永远必须保留。
- B：确认本机及当前 B 任务对上述9个旧 checkpoint、两项 X-VLA 下载残片是否有读取/下载恢复依赖；报告具体使用路径或无使用结论。不要重启旧 Smol/X 队列。
- A：核查 B 提交的两项 X-VLA 下载残片，确认保留的完整 `model.safetensors` 与已知源身份一致、下载已完成且无本机写入者；结合 B 无写入/恢复回执后交清理建议。只核对具体 VLA 文件，其他项目不动。
- 两端：区分“历史库存记录”与“本轮/封存实验真正需要保留的文件”。库存记录本身可保留并追加删除沿革，不能因此把所有中间权重永久判为依赖；真正的选模、恢复、复现或共享读取依赖必须保留。

各写 `receipts/<role>/STORAGE_DEPENDENCY_REVIEW_V1.json`，引用原候选身份、明确核查范围/未知项与建议。分析端收到后决定是否发布精确 delete 清单。该工作不阻塞必要预检修正，也不允许执行端自行删除。
