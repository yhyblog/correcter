## 2. Random-once：预抽时机，不读取未来

唯一冻结随机表`RANDOM_ONCE_SCHEDULE_V1.json`覆盖2500个(source,H)；R/Post/Velocity共用同一项。表由原`A/config/TEST_SOURCES_V1.json`和固定随机域生成，不读取轨迹、G0、触发次数、成功或旧once结果。策略自然噪声与candidate噪声不受抽时机影响。

t表示**已经执行的控制步数**，在下一条动作前判定；t=5不是第五条动作之前。无先前干预时的潜在合法槽：

`S_H = {t ∈ {5,10,...,290} : 0 < t mod H <= H-5}`。

H10/20/30/40/50的槽数依次29/44/49/51/53。在运行前均匀抽一个槽t_random，冻结表是唯一权威输入。不用每episode后验轨迹长度缩短取样区间，不按G0实际触发子集入组，不根据成功挑随机seed。

到t_random时仍需通过原来的合法性判断：先按原次序自然refill；每5步、历史成熟、queue age>0、余旧动作至少5条、距离300步至少10条、当前不在承诺锁内。满足则执行一次该分支的干预；**只有G0>.05这一选时机条件被随机计划替换**。正常调用context/D/G0可保留为shadow，数值只记录不控制Random触发，也不增第二套前向。

若在t_random前已成功/终止，或该时刻实际不合法：不干预、不顺延、不补抽、不强迫走到时点，保存原因；该源仍在全500分母。至多一次。Random-once不是“每源保证一次”，这是合法的在线策略定义。

随机R/P/V使用同一t_random和同一源的正常策略seed。若运行前配置/表身份不一致，先CPU修正再入任务；不做逐像素/逐动作跨机证明，不重跑N或once作为预检。

## 3. G0-multi：只取消总次数帽

复用当前主表G0-once的全部合法性、D5历史/成熟、每5步检查、阈值严格>0.05及下游算法，仅删除`intervention_count < 1`的总次数限制。禁止新增任意max-count、冷却或不同阈值，也不把低于阈值的随机报警加入此模式。

每次干预C10期间不重入；C10完成后丢弃raw尾部/隐藏旧队列，再按该格native H恢复。恢复边界age=0仍不合法；继续到下一原本合法监测点才可能再触发。300步总预算、提前成功/终止条件不变。按这些规则推导最多20次干预，只用于资源估计，不能写成新人为次数帽。

每次保存cut列表和事件。原main实现若把`first_cut=t`每次覆盖，必要修复为仅首次赋值；保留`last_cut`及完整`intervention_cuts`，不能在汇总中将multi压成一次。
